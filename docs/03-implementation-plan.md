# VOCAL LISTENING LAB — 実装計画 v0.1

設計日：2026-10-05。今回の納品範囲は設計資料。以下は次の実装工程の計画であり、アプリ本体や公開設定の完了報告ではない。

## 1. 技術方針

`bass-study`と同じく、Pythonのビルド処理、素のJavaScript、CSS、JSONを使う静的アプリとする。生成物は`dist/index.html`を基本にし、GitHub Pagesのプロジェクトパスで動く。新しいフレームワーク、バックエンド、認証、データベースは初期版に加えない。

理由は、今回の価値の中心が教材と、再生・比較・保存の一連の体験にあるため。小さな静的構成のまま、画面ロジックと教材データを分離して更新しやすくする。

## 3. データ契約

### 3.1 コース

| フィールド | 型・意味 | 制約 |
|---|---|---|
| `schemaVersion` | 整数 | 初版1。教材の編集回数とは分ける |
| `courseId` | 文字列 | `vocal-listening-lab`固定 |
| `contentVersion` | 文字列 | 原稿・選曲更新の版 |
| `title` / `subtitle` | 文字列 | 表示名 |
| `playlist` | オブジェクトまたはnull | 確認前はnull |
| `sections` | 区分の配列 | 回のIDを参照し、位置で切り分けない |
| `lessons` | 回の配列 | 安定した`lesson-01`等のID |

`playlist`には`spotifyId`、`verifiedAt`、`recordingOrder`、`mismatches`を持たせる。`recordingOrder`は内部録音IDの列、`mismatches`は該当内部IDと理由の列。順番と録音の同一性は別々に確認する。

### 3.2 レッスン

必須項目：`id`、`order`、`title`、`lead`、`goal`、`lecture[]`、`coreRecordingIds[2]`、`extraRecordingIds[1]`、`focusAxes[]`、`question`、`reflectionExample`、`exerciseId`、`silentAlternative`、`notePrompt`。

- 初期完成版は14件だが、描画や保存の有効ID判定は件数のハードコードにしない。
- 基本／発展の集合は重複させず、各録音の主な所属回は一つ。
- `reflectionExample`は正答ではなく観察例と表示する。
- `quickMinutes`と`deepMinutes`は目安。音声再生時間から学習完了を自動判定しない。

### 3.3 録音

| フィールド群 | 例・用途 |
|---|---|
| 識別 | `id: rec-001`、曲名、表示アーティスト、関連する`artistIds[]` |
| 歌唱担当 | `performers[]`：人物ID、lead/co-lead/backing等、クレジット出典。未確認を許容 |
| 版 | アルバム、原リリース年、録音年（不明可）、live/studio、配信版名、mono/stereo/mix補足 |
| 配信先 | Spotify track ID、公式代替URL、各URLの検証状態と確認日 |
| 本文 | 一文、背景、観察解説、三つの聴き方、注意点、問い |
| 聴く場所 | 必須の場面記述、任意の開始／終了秒、照合した配信ID |
| 実践 | 実験ID、歌わない代替、観察専用かどうか |
| 検索 | ジャンル、言語、観察軸、別表記・読み |
| 編集状態 | `draft / metadata-verified / audio-reviewed / publish-ready` |
| 根拠 | `claims[]`と`sourceIds[]`、確認メモ、最終確認日 |

録音年と発売年は別。年が分からなければnullにする。未知の歌唱担当、制作手法、機材を空欄埋めのために推測しない。

秒数は場面説明の補助。開始・終了は同じ録音版に対し、0以上・開始より終了が大きい・確認した長さ以内を検査する。秒数からSpotify曲を自動シークできるという機能は前提にしない。

### 3.4 人物・グループ

`id`、`name`、`aliases[]`、`kind: person|group`、`bio`、`listeningPoints[]`、`recordingIds[]`、`compareArtistIds[]`、`experimentIds[]`、`claims[]`。

機材・制作の主張は`scope: specific-recording|period|general`を付ける。特定録音にはその録音IDと対応資料が必要。情報が無い場合は公開画面に「この録音の機材は確認できていません」と短く示すか、任意項目を非表示にする。

### 3.5 出典と主張

`source`：ID、著者／団体、タイトル、URL、資料種別、確認日。

`claim`：ID、対象、主張文、`kind: factual|listening-prompt|experiment`、`sourceIds[]`。

事実の裏付けに公式トップページだけを当てず、対象情報があるページを選ぶ。聴く問いと実験の提案を、資料の引用として表示しない。参考資料と事実の証拠を区別する。

## 4. 保存データ契約

```json
{
  "format": "vocal-listening-lab",
  "version": 1,
  "courseId": "vocal-listening-lab",
  "contentVersion": "1.0.0",
  "exportedAt": "ISO-8601",
  "state": {
    "lessonCompleted": {"lesson-01": true},
    "recordingObserved": {"rec-001": true},
    "notes": {"lesson:lesson-01": "自分の観察"},
    "lastLessonId": "lesson-01",
    "learningMode": "listen",
    "updatedAtByField": {"notes.lesson:lesson-01": "ISO-8601"}
  }
}
```

これは契約の説明用。日時の説明文字列を本番のサンプルとして読み込ませない。

- メモキーは`lesson:<id>`、`recording:<id>`、`comparison:<id>`に限定。
- 初期実装ではメモ1件20,000文字、JSONファイル2MBを上限とする。実装で上限値を一か所に定義し、UIにも超過理由を示す。
- 全データが有効か確かめてから、復元確認を表示。教材ID不一致や非対応版は拒否する。
- 同じ教材の古い`contentVersion`は、既知IDを引き継ぎ、未知IDを報告して扱いを選べるようにする。黙って消さない。
- 配列・null・想定外の型・危険なオブジェクトキーを拒否。HTMLとして実行せず、すべてテキストとして表示する。
- 保存成功後に状態表示を更新。保存不能時もメモリ上の新しい入力をJSON／TXT出力できる。
- 壊れた保存値は上書き禁止の回復モードにし、元データの書き出し後に明示的に初期化できる。
- 別タブから受け取った変更を項目単位で反映する。同一メモの競合では編集中テキストを保持し、両方を見て選べるようにする。
- バックアップと復元に音声ファイルは含めない。

## 6. 作業順と成果物

### P0：設計の固定 — 今回

- 空のvocal-studyに設計資料を保存。
- 前提・候補・確認済み事項を区別。
- アプリコード、Actions、公開サイトは作らない。

**成果物：** README＋4設計書。**今回の完了条件：** 文書間の件数、ID、リンク、範囲が整合し、GitHubに保存されている。

### P1：録音カタログを確定する

1. 42曲の候補について公式カタログ・クレジット・配信先を照合する。
2. 表示アーティストと実際の歌唱者の対応を確認する。
3. 日本で開ける指定録音のURLとIDを保存する。
4. 基本28曲・発展14曲の教育目的を点検し、採用／代替を決める。
5. 対象版で観察区間を実聴レビューし、秒数を使う場合はその版に結びつける。
6. プレイリストURLがある場合は教材と照合する。まだ無い場合はnullのまま進める。

**成果物：** 全曲メタデータ、出典、歌唱担当、観察区間、未確定事項の解消記録。

**通過条件：** 曲名の検索結果だけを確定リンクとして扱っていない。未確認の配信IDを作らない。音声へアクセスできない場合はレビュー待ちとし、全件確認済みと報告しない。

### P2：最初の1回を端から端まで作る

1. データ検証と静的ビルドを用意する。
2. Lesson 1の3曲、関連人物、人物から曲へ戻るリンクを実装。
3. 曲の展開、Spotifyの読み込み、比較、メモ、学習済みを実装。
4. 保存、TXT／JSON出力、復元、保存エラーを実装。
5. iPhone幅とキーボード操作で一連の流れを確認。

**成果物：** Lesson 1だけで使えるローカル試作。**通過条件：** 再読み込みしてメモが残り、バックアップを別のブラウザ状態に復元できる。残り13回を完成扱いにしない。

### P3：教材を全14回へ展開する

- 編集初稿を基に42曲の詳細原稿を完成。
- 全登場歌手・グループのプロフィールを関連録音へ紐づける。
- 6組以上の聴き比べ、基礎用語、14回の振り返りを完成。
- 歴史・人物・録音の事実を出典へ対応させる。
- 高音・歪みの聴く課題、全実践の無発声代替を確認。

**成果物：** 全教材JSON。**通過条件：** 42曲すべてが公開用の状態を満たす。仮文や「あとで調べる」を本番画面に残さない。

### P4：録音実験と索引を仕上げる

- 8本の録音実験、声の短い実験、関連導線を実装。
- 検索で日本語・英語・別表記に対応。
- 歌わないモード、最後の回へ戻る機能を実装。
- 長い人物解説・出典を読んでも元の曲へ戻りやすくする。
- クリックはユーザー操作で始め、ページ移動・非表示で停止。正確な楽曲同期は約束しない。

**成果物：** 全画面が揃った公開候補。**通過条件：** 用語→曲→人物→実験の参照が解決し、モバイルで迷わず元へ戻れる。

### P5：内容と操作を監査する

- 下記の受け入れ条件を実行し、結果を記録。
- 実際のiPhone SafariとChromeで基本動線を確認。エミュレーションのみの場合はそう明記する。
- 字の大きさ、折りたたみ、キーボード表示、外部アプリからの復帰を確認。
- 実聴レビューと配信版照合を最終確認。自動リンク検査だけで代替しない。

**成果物：** 監査結果と修正済み公開候補。**通過条件：** 保存データ喪失、誤録音、主要導線不能などの重大問題がゼロ。

### P6：GitHub Pagesに公開する

公開作業を進める段階で、リポジトリのPages設定を確認してActionsを導入。プレビュー／ビルド成果物で内容を確認し、公開対象コミットを固定する。公開URLは成功したワークフローまたはGitHubの設定から取得し、事前に公開済みURLとして案内しない。

**成果物：** 公開URL、対応コミット、READMEの利用案内。**通過条件：** 公開先で初回読込、直接リンク、Spotify導線、保存・復元が動く。更新時も旧メモのIDを保持。

## 8. 手動レビューが必要な境界

自動化できるのは、ID、参照、形式、保存ロジック、表示・操作の一部。正しいテイクか、解説の聴きどころが聞き取れるか、歴史の説明が適切かは別途レビューが必要。

音源を聴けない環境では、その項目を未確認として残す。Spotify検索結果の一致や埋め込み表示だけでは音声レビュー済みにしない。実装者が勝手に録音年・秒数・声域・声帯動作を埋めて完了させない。

## 9. 変更と公開の運用

- 設計書を起点に実装ブランチを作り、P2の縦の試作と全教材展開を別のレビュー単位にする。
- Pages公開用ワークフローを早期にmainへ置いて、文書更新で未完成教材が公開される状態を避ける。
- 選曲差し替えは新録音IDを発行し、旧IDのメモを保持。意味の違う曲へ同じIDを再利用しない。
- Spotify IDの変更だけで同一録音を置き換える場合も、照合理由・確認日を残す。
- 人物・機材情報は、更新対象の主張と出典だけを改訂し、手校閲済み情報を一括生成で上書きしない。
- 公開後の修正はコードと本文の版を対応させる。ロールバックでも保存データは消去しない。

最初の着手点はP1の録音カタログ確認。Lesson 1の3曲を優先して指定録音と観察箇所を確定し、P2の試作へ進む。全曲の録音調査と詳細執筆はその後も進められるが、公開判定では42曲すべてを揃える。利用者のジャンル嗜好が後から分かった場合は、基本28曲の学習目標を保って発展14曲から調整する。
